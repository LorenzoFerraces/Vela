Building Cryptographic Proofs: 
Zero-Knowledge Proofs & SNARKs 
Final Project – Extending/Finding a SNARK 
Application from the Literature 
39th Escuela de Ciencias Informáticas (ECI), University of Buenos Aires – July 2026 
1. Overview 
The final evaluation of the course is a project in which you will select a research paper that 
presents an application of SNARKs, published at a cryptography or applied-cryptography 
venue, and propose and (partially) implement a motivated extension of its contribution. 
 
The goal is to reproduce, in a small scale, the workflow of applied cryptographic research: 
understand an existing system, identify its limitations, argue which improvements are feasible, 
implement a meaningful subset of them, and measure the result honestly. 
Otherwise, you understand how a solution works and then you find a valuable application of this 
solution.

5. Deliverable 
The deliverable is a public GitHub repository containing: 
●​ A README (the main written report) answering the questions in Section 6. The README 
should contain at most 1500 words. 
●​ The source code of your implementation, with clear build/run instructions so that results 
are reproducible. 
●​ The benchmark scripts and raw measurements used to produce your performance 
numbers. 
●​ It is recommended to set up Continuous Integration (e.g., GitHub Actions) running a unit 
test suite that demonstrates completeness (a valid witness produces a proof accepted by 
the verifier) and soundness (an invalid witness is correctly rejected) of your 
implementation. 
●​ You can optionally add to the repository a link to a video with a demo of your work. 
 
Submit the repository URL via Google Classroom by the deadline.  
The repository state at the deadline (last commit before the deadline) is what will be graded. 
6. Required Content (README Structure) 
Your README must answer, at minimum, the following questions: 
 
1.​ The application. What problem does the paper solve, and what role does the 
zero-knowledge proof play in the system? What exactly is being proven, by whom, and to 
whom? What are the statement, the witness, and the trust assumptions? 
2.​ The proof system and framework. Which SNARK (or proof system) does the paper use, 
and which framework/library implements it? What are the relevant properties (transparent 
vs. trusted setup, proof size, verifier cost, recursion support, etc.)? 
3.​ What can be improved/On what the solution can be used. Identify limitations of the 
paper's construction or implementation (e.g., prover time, proof size, expressiveness of 
the statement, deployment constraints, security assumptions) and propose one or more 
concrete extensions, with a clear motivation for each. 
4.​ Feasibility analysis. For each proposed extension, argue whether it is feasible within the 
scope of this project and why. Distinguish explicitly between improvements that are 
feasible but out of scope, improvements that are open research problems, and 
improvements you actually implemented. 
5.​ Your implementation. What did you implement, using which framework, and why that 
framework? Describe the design and any deviations from your original plan. How did you 
test the correctness of your implementation (completeness and soundness)? If you set up 
a CI pipeline, include a link/badge to it. 
6.​ Performance. Report the performance of your implementation (at least: proving time, 
verification time, proof size; specify the hardware used). Compare against a baseline: the 
numbers reported in the original paper (if available and comparable) and/or a naive 
baseline you define and justify. Isolated numbers without a comparison point will not be 
considered meaningful.

7. Grading Rubric 
●​ Understanding (1) of the paper, (2) of the role of the zk-proof and implementation 
(questions 1–2). 
●​ Quality and originality of the proposed extension(s), and strength of the motivation 
(question 3). 
●​ Feasibility analysis: correctness and honesty of the assessment (question 4). 
●​ Implementation: correctness, scope, and code quality (question 5) — including whether 
tests (ideally run via CI) demonstrate completeness/soundness, not just absence of 
runtime errors. 
●​ Benchmarking rigor: methodology, baseline comparison, reproducibility (question 6). 
●​ Clarity and organization of the repository and README. 
 
Academic integrity. You may use any tool, including AI assistants, but you are fully responsible 
for everything in your repository and you must be able to explain and defend every design 
choice and every line of code. Reusing third-party code is allowed only with clear attribution.
